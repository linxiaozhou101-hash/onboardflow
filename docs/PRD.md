# 入职服务工作台 · 产品说明

本项目采用模拟入职服务场景，全部人物、制度和业务参数只用于作品演示。本项目由 Codex 辅助编码；问题选择依据用户提供的公开岗位与产品资料，不声称已开展真实企业访谈，不声称存在可量化业务收益。

## 问题与目标

员工查政策、准备材料、联系 HR 和追踪 IT 任务常发生在不同入口。作品选取“入职准备与首周异常处理”，让员工看到适用于自己的依据、负责人员、仍缺什么及下一步；让 HR 通过事件追溯服务阻塞点。此范围是可实施性判断，不代表全行业痛点排序。

## 三类任务

|任务|用户成功条件|系统边界|
|---|---|---|
|S1 准备什么、去哪报到|按已验证城市、雇佣类型和计划入职日查询；能打开对应版本条款|缺条件先问；无依据或范围冲突转人工|
|S2 缺失材料补交申请|员工预览并确认请求，HR 明确批准延期或拒绝，员工确认结果|批准申请不等于材料收齐；后续补交单独跟进|
|S3 账号设备异常|先查已有记录；HR 分派 IT，任务完成后 HR 给结果，员工确认|IT 仅执行本地演示任务，不实际开通任何账号|

## 优先级与取舍

P0 是服务闭环、对象权限、数据库事务和材料真实性边界；P1 是知识版本、运营分析和离线评价。范围不包含招聘决策、薪酬社保计算、OCR、真实 HRIS、真实证件上传或公开部署。

后端采用 FastAPI/Pydantic 与 SQLite 原生 SQL，避免本地原型增加 ORM 迁移和服务部署负担。事务使用数据库锁与对象行版本同时约束。前端 React/TypeScript/Vite，默认离线检索；中文字符 n-gram 可处理无空格中文。所有判断权保留在后端规则，模型仅可草拟文本。

SLA 使用连续自然小时，等待员工不暂停，重开不重置到期。参数是虚构目标，不是企业承诺。看板仅从实际写入的模拟记录与事件计算。

## 岗位能力映射

|能力|可展示产物|
|---|---|
|需求分析与员工体验|三任务边界、任务卡、信息缺失追问、输入保留|
|流程设计与系统交付|跨角色状态流、必需任务依赖、审批/材料分离|
|知识运营与数据治理|适用范围、版本接续、引用审计、角色过滤|
|数据分析与评价|明确分母、阻断提交入统计、合成验收与人工语义复核分开|
|AI 应用|可替换适配器、无 Key 离线、非法引用回退、人工审批|

## 验收与预设目标

适用性、权限、幂等和非法状态的关键检查目标是全部通过；可答类自动筛查目标为至少 90%。这些是预设目标。实际运行结果以 `reports/evaluation.json` 和测试报告为准；自动事实匹配不等同于人工语义准确率。
